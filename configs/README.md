# Config files

Each YAML file describes one set of runs; `src.generate`, `src.evaluate`, `src.timing` and
`src.hybrid` take all their settings from it.

| Field | Meaning |
| --- | --- |
| `experiment` | Experiment ID such as `e1`, `e2` or `smoke`; it sets the output folder. Exploratory runs use their own ID (e.g. `e2_exploratory`, `c_smoke_exploratory`) so they never mix with the main results |
| `split` | `tune` / `eval` / `diversity`, read from `data/splits/<split>.jsonl`; `prompts_file` can point to another prompt file. **Required** even with `prompts_file`, because it sets the output folder (E5 uses `split: parti`) |
| `prompts_file` | Custom prompt file (JSONL, each line with at least `prompt_id` and `prompt`), used by E5 |
| `limit` | Use only the first N prompts (for debugging) |
| `seeds` | Seed list; each prompt gets one image per seed |
| `method` | `sdxl_base` / `lcm_lora` / `sdxl_turbo` / `sdxl_lightning`; the E4 two-stage method is `hybrid` and runs only through `src.hybrid` |
| `resolution` | Generation resolution (512 for SDXL-Turbo, 1024 for the others); SDXL-Turbo at 1024 is only an exploratory reference (`configs/e1/sdxl_turbo_1024.yaml`) |
| `dtype` | Precision, `fp16` by default |
| `models` | `{repository: revision}`, pinned to the revisions used in all runs |
| `timestep_spacing` | Baseline and E4 refinement stage only: the scheduler's timestep spacing, `trailing` by default (the first step starts at t = 999) |
| `lightning_steps` | Which SDXL-Lightning checkpoint to use (1 / 2 / 4 / 8 steps) |
| `lora_fuse`, `lora_scale` | Whether LCM-LoRA is fused, and its adapter scale; E3 uses `lora_fuse: false` |
| `exploratory` | `true` allows settings outside the authors' recommended range (e.g. CFG for SDXL-Turbo or SDXL-Lightning, or the 1-step SDXL-Lightning checkpoint) and marks reference runs outside the main protocol (e.g. SDXL-Turbo at 1024). It applies to the whole file, so exploratory configs live in their own file, never in the same grid as main configs; such files are never used for selection |
| `name` | Output subfolder of a single config; generated from the settings when omitted. With `grid` it is always generated and includes every swept field |
| `save_size` | Size of the saved images, 512 by default (all metrics are computed at 512, and this saves disk quota) |
| `full_res_first_n` | Also save full-resolution copies of the first N prompts to `full/`, 20 by default, for detail crops; skipped when the images are already at the saved size (e.g. SDXL-Turbo at 512) |
| `params` | Arguments passed to the pipeline call, such as `num_inference_steps`, `guidance_scale` and `strength` |
| `grid` | Parameter grid; every combination becomes one config point |
| `draft` | E4 (`method: hybrid`) only: call arguments of the SDXL-Turbo draft stage, always at 512 with guidance 0 |
| `refine_seeds` | E4 only: noise seeds of the img2img stage, paired with `seeds` by position, so both lists must have the same length |
| `refine` | E4 only: `false` keeps only the upscaled draft (the no-refine control); `params` and `refine_seeds` are then omitted |

## Grids

Each `grid` field goes to the right place automatically: fields from the table above (such
as `lightning_steps`, `lora_scale`, `resolution`, `timestep_spacing` and `dtype`) override
the top-level value, and any other field goes into `params`. For example, the E3 adapter
scale sweep:

```yaml
method: lcm_lora
lora_fuse: false
lora_scale: 1.0
params:
  num_inference_steps: 8
  guidance_scale: 2.0
grid:
  lora_scale: [0.25, 0.5, 0.75, 1.0]
```

For SDXL-Lightning, `num_inference_steps` is set from `lightning_steps` by the code, so the
step count always matches the checkpoint; do not set it in `params`. SDXL-Turbo and
SDXL-Lightning default to `guidance_scale` 0.

## E4 two-stage method (`src.hybrid`)

Configs with `method: hybrid` are generated by `python -m src.hybrid`: SDXL-Turbo makes a
512 draft, which is upscaled bicubically in pixel space to `resolution` and refined by SDXL
base image-to-image (DPM-Solver++ with `timestep_spacing`). `params` holds the img2img call
arguments and must include `strength`; `models` lists both the SDXL-Turbo and the SDXL base
revisions. Each draft is generated once and refined at every strength of the grid, so the
points of one file may only sweep `params`. Images keep the draft seed in their names, so
`src.evaluate` and `src.select_configs` work as usual. The `calls_*.jsonl` logs record the
UNet calls actually executed in each stage, with batch sizes and timesteps; with CFG the
conditional and unconditional branches run together as one call with batch size 2. Timing
uses `python -m src.hybrid --config <file> --timing`, with the same protocol as
`src.timing`, over the whole two-stage pipeline.

## Automatic checks

- An unknown top-level field (e.g. a misspelt name) is an error.
- A field from the table above inside `params` is an error; a `params` name the pipeline
  does not accept is reported after the model is loaded and before the first image.
- Two points of one grid with the same folder name are an error.
- Guidance outside a method's valid range (0 for SDXL-Turbo and SDXL-Lightning, at most 2.0
  for LCM-LoRA) is an error unless `exploratory: true`. A step count in an SDXL-Lightning
  `params` that differs from `lightning_steps` is an error; `lightning_steps: 1` requires
  `exploratory: true`; `timestep_spacing` is allowed only for `sdxl_base` and `hybrid`.
- Before generating or scoring, every output folder is checked: if its `config.yaml`
  differs from the current settings, the run stops before using any GPU time, so images
  made with different settings are never scored together. To rerun, choose a new name or
  move the old folder away.
- Scoring an incomplete set of images is an error unless `--allow-partial` is given.
- An unknown name passed to `--only` is an error.

## Folders

- `configs/e1/`: every method's frozen E1 configs and selection records `selection_<method>.json`,
  plus the 8-step baseline reference (`sdxl_base_8step.yaml`) and the exploratory SDXL-Turbo
  1024 config (`sdxl_turbo_1024.yaml`).
- `configs/e2/`, `configs/e3/`, `configs/e4/`: tuning grids and evaluation configs of each
  experiment; `configs/e3/` and `configs/e4/` also hold their selection records.
- `configs/e2/sdxl_base_spacing.yaml`: timestep-spacing check of the baseline ("leading"
  spacing at 4, 8 and 15 steps, experiment `e2_spacing`), compared pairwise with the
  trailing points of the E2 sweep and never used for selection; intervals come from
  `python -m src.bootstrap_ci`.
- `configs/e5/`: the E5 configs at each method's frozen E1 quality point, the frozen
  PartiPrompts list and its review sheet.
- `configs/c_frozen/`: per-point E1 configs, diversity configs (`diversity/`) and manifests
  (including the SHA-256 of the data splits) written by `python -m roles.c.workflow freeze`;
  rerunning it stops if the result differs from the stored records.
- `configs/smoke/`, `configs/c_smoke/`: smoke tests.

Outputs go to `outputs/<experiment>/<split>/<method>/<name>/`: images `<prompt_id>_<seed>.png`,
`config.yaml`, one `run_info_<shard>.json` per shard (library versions, GPU, model
revisions, scheduler settings) and the UNet call log `calls_<shard>.jsonl`.
